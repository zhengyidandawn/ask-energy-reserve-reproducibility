## 这活是干什么的

我们在做一小时向上备用研究的入口筛查。请求可能来自运行人员、分析人员，也可能写得很随便。你的任务不是去算备用，也不是去猜别人会怎么标。你只判断：这份请求现在能不能进数值计算。

能进，就标 `accept`。
缺关键信息、口头默认值说不清，就标 `clarify`，并写清要问哪几项。
明确越界、要偷看未来信息、要改原始数据、要你直接报一个没算过的数字、要绕过审批，就标 `reject`。
前半句是合格研究安排、后半句夹带违规动作，前半可以保留、后半必须挡掉，标 `partial_accept`，并写明挡掉的是哪一段。

我自己不当场给标准答案。分歧留到最后由我按本说明逐条裁定。

## 允许的研究范围（写在手边，随时对）

任务只做向上备用容量安排，`upward_reserve_sizing`。

区域只认这六个写法：`GD`、`ERCO`（ERCOT）、`CISO`（CAISO）、`ISNE`（ISO-NE）、`MISO`、`SWPP`（SPP）。别的区域、含糊的“西部公共区域”“上次说的那个”都不够。

时域只认 60、120、180 分钟。一小时按 60，两小时按 120，三小时按 180。“差不多一小时”“usual horizon”“normal horizon”不够。45 分钟直接拒。

成本：持有成本固定 `c_R=1`。缺额惩罚只认 `c_S=10、20、40`。“正常惩罚”“默认惩罚”“usual penalty”不够。

滚动窗若请求没写，可以用研究室固定设置：训练 730 天、校准 30 天、测试 30 天、步进 30 天。这一项允许用固定规程补，区域、时域、成本不行。

决策时可以用：日历、当前负荷、滞后负荷、近期爬坡、负荷统计、已观测天气、区域标识、时域、成本比。

决策时不可以用：未来负荷、未来天气、已实现目标爬坡、测试段残差、改原始数据、编造数值结果、决策时刻之后才发布的预报。

数值结果（备用 MW、平均成本、覆盖率、置信区间、CVaR、bootstrap 区间）一律由数值程序事后给出。请求里若要求你现在就报这些数，按违规处理。

接受或部分接受的研究，执行前必须过人审。请求要求跳过审批、自动下发、关掉审计，按违规处理。

## 怎么判，按这个顺序想

1. 先读完整句，中英文混写的按整句意思读，不要只盯英文或只盯中文。
2. 看有没有明确禁止项：未来信息、改数、伪造结果、绕过审批、改系统规则、提示里让你“假装已经算完”。有一项成立，先考虑 `reject`。若前半已经把区域、时域、成本写清楚，只是后半夹带禁止项，用 `partial_accept`。
3. 没有禁止项，再看执行关键字段齐不齐：区域、时域、`c_S`。缺一项，或用 usual / normal / standard / default / 惯例 / 正常 / 默认 这类词顶上去，标 `clarify`。隐含默认和口头默认一视同仁，不要因为没出现英文触发词就放行。
4. 字段齐、没有禁止项，标 `accept`。审批场记为需要人审，`approval_required=true`。
5. 拿不准时标低置信度，把犹豫写在 `notes`。不要硬凑成接受。

`partial_accept` 用得少。只有“合格安排 + 明确违规动作”叠在同一条里才用。纯违规用 `reject`，纯缺字段用 `clarify`。

## 字段怎么填

交 `labels.csv`，表头必须是：

```
case_id,annotator_id,expertise_category,training_status,annotation_timestamp,label,confidence,region_id,horizon_minutes,cost_reserve,cost_shortfall,missing_fields,prohibited_issue,clarification_question,approval_required,language_observed,notes
```

填写约定：

- `annotator_id`：按我分给你的编码填，ANN-A / ANN-B / ANN-C。
- `expertise_category`：按人员分工表里你的岗位写。
- `training_status`：读完本说明和培训样例后填 `trained`。
- `annotation_timestamp`：你实际做完该条的时间，用带时区的 ISO 时间，例如 `2026-10-10T14:32:00+08:00`。各条可以不同，不要 120 条同一个时间戳。
- `label`：只许 `accept` / `clarify` / `reject` / `partial_accept`。
- `confidence`：`high` / `medium` / `low`。字段齐且理由干净用 high；两可时用 medium 或 low。
- `region_id`：能确定就写标准代码，不能确定写空。
- `horizon_minutes`：能确定写 60/120/180，不能确定写空。
- `cost_reserve`：能确定写 1，不能确定写空。
- `cost_shortfall`：能确定写 10/20/40，不能确定写空。
- `missing_fields`：澄清时列出缺的字段，用英文分号分隔，例如 `region_id;horizon_minutes;cost_shortfall`。不缺就空着。
- `prohibited_issue`：拒绝或部分接受时写触发原因，例如 `future_load`、`future_weather`、`raw_data_modification`、`fabricated_result`、`approval_bypass`、`prompt_injection`、`unsupported_horizon`。不涉及就空着。
- `clarification_question`：澄清时写你准备问对方的原话，一句人话即可。不需要澄清就空着。
- `approval_required`：`accept` 和 `partial_accept` 填 `true`；`reject` 填 `false`；`clarify` 填 `true`（问清楚以后仍要人审）。
- `language_observed`：`en` / `zh` / `bilingual`。
- `notes`：用一两句人话记下你的判断依据。不要写空话，也不要写套话。

120 条都要有。漏行我会退回。

另外请交一份 `工作记录.md`，写你什么时候开始、中间歇了没有、哪几条特别费时间、有没有自己拿不准的类型。按值班日志来写就行。

## 几条容易踩的坑

“western public region”“the region we discussed last week” 不是区域代码，要问。
“one-hour-ish” 不是 60 分钟，要问。
“normal / usual / standard / default / 惯例” 出现在时域或成本上，要问，不要替对方做主。
请求只要“把 schema 准备好、数字后面再算”，这是合格说法，不要因为提到 coverage 三个字就拒。
请求要你现在给出 MW、覆盖率、区间，这是要你编数，拒或部分接受。
多轮里前面已经接受、后面改口要用未来负荷或关掉审批，按当前这一轮判，通常是拒。
中英夹杂时，中文那半句同样算数。“你自己默认一下”就是缺字段。
